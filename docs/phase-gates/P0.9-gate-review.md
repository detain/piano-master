This document is the written Phase-0 gate review required by plan §20 P0.9. It is a
DRAFT because the two hardware-dependent spikes (P0.2/P0.3/P0.5 device measurement and
P0.4 MIDI) and the P0.8 rights vetting have not yet been run; the two manual backend

## 1. Executive summary

Phase 0 shipped three of its hardware-independent spikes to green: the monophonic pitch
harness (P0.2-A3, 88/88 A0–C8 with 0 octave errors), the offline evaluation harness with
calibration proven against mir_eval (P0.3.1, metric agreement to 1e-9), and the backend
runtime spike (P0.6-C: k6 baseline, reload and failover drills, ADR-0002). The P0.6.3
soak and P0.6.4 restart-mid-consume drill completed on 2026-08-22
(docs/runbooks/soak-results-2026-08-22.md): 23.4 M requests over one hour at ~6510 rps
with 0 errors, 0 bleed, and 0 kB RSS growth, and no job loss across a Dragonfly restart.
The one remaining backend gap is the MySQL reconnect path — a forced connection kill
returns HTTP 500 until the ~50 s pool heartbeat; a fix and regression test are in
progress (see §5). The Oboe/JNI
audio pipeline (P0.2-B) and the scrolling-notation prototype (P0.5, both skins with
Bravura and JankStats) are code-complete with green JVM host tests but are **unmeasured
on device**. The polyphonic bake-off (P0.3.3) is **blocked at the dependency level**:
no published OAF TFLite artifact exists and the Python 3.12 environment cannot install
the OAF interpreter or Basic Pitch's pinned TensorFlow; the engine YIN baseline remains
the only scoring floor (F1 = 1.0 on clean synthetic). P0.4 (MIDI), P0.7 (ground-truth
corpus), and P0.8 (rights) have **not started** — all three require hardware or
legal/content work that is not yet on the bench.

**Recommended decision: go-with-cuts.** The detection and latency gates cannot be
adjudicated until the test phones and DGX-520 arrive, and the dependency-blocked bake-off
cannot proceed without a Python < 3.12 environment or a published model artifact. The
plan's Phase-0 gates exist to de-risk the two hardest claims — "note appears in under
80 ms" and "polyphonic chord detection works on cheap hardware" — and neither claim has
been measured. Proceeding to Phase-1 *planning and hardware-free work* is justified
under §20 P0.9 options (b)/(c) logic: the monophonic-plus-simple-chords scope (c) and the
MIDI-first posture (b) remain viable fallbacks, and the tracks that do not need a device
(SongPack v1 spec + golden fixtures, pipeline CLI v0, scoring-engine internals) are
pre-requisites for every subsequent phase regardless of which detection path wins. The
gate verdict on detection and latency is **deferred**, not waived: it must be re-run with
device evidence before Phase-1 completion.

## 3. Latency budget table (P0.2.4)

The P0.2.4 rig decomposes the note-to-screen loop into six stages so the total is
optimizable (§20 P0.2.4: "You cannot optimize what you have not decomposed"). The
internal instrumentation hooks below exist in the P0.2-B code; the measured values are
**pending device** — no phone has run the rig yet.

| Stage | What it measures | Instrumentation hook (exists in code) | Measured value |
|---|---|---|---|
| Hardware in | Time from hammer strike / mic arrival to audio available | Oboe granted-property logging (device → granted mode / frames-per-burst / sample rate; catches silent shared-mode downgrades) | **Pending device** |
| Buffer | Time in the lock-free SPSC NoteEventQueue | Ring-buffer write timestamp; NoteEvent drop counter (must stay 0 in soak) | **Pending device** |
| Detect | YIN/pYIN inference over 2048-sample windows, 50% overlap, worker thread | Detector-output timestamp (internal instrumentation per §20 P0.2.4) | **Pending device** |
| Bridge | JNI hand-off of NoteEvent structs to Kotlin Flow | JNI bridge timestamp; drop counter at the queue drain | **Pending device** |
| Render | Compose frame present for the note-name/notation update | JankStats (metrics-performance 1.0.0, tag KeyQuestJank) frame timings | **Pending device** |
| Display | True human-perceived display latency (invisible to software) | High-speed camera (240 fps phone slo-mo): film hammer strike + screen together, count frames | **Pending device** |

**Gate contribution (§20 P0.2.4):** < 80 ms note-to-screen on the mid-tier device,
< 120 ms worst case across all five. The six stages must sum to the measured total
± 5 ms. The rig protocol is defined in plan §20 P0.2.4 (loopback cross-correlation,
high-speed camera, internal instrumentation); no separate runbook file has been written
yet — the drill itself is the remaining work.

## 4. Model decision status (P0.3.6)

The written model decision (P0.3.6 ADR) is **deferred**: there is no bake-off result to
decide on, because two of the three candidate builds are dependency-blocked.

**Confirmed floor (not blocked):**
- **Engine YIN baseline** (`engine/tools/yin_cli.cpp`): F1 = 1.0000, onset median
  0.0107 s, 10/10 notes on the clean 10-note synthetic melody (pipeline/README.md).
  This is the confirmed monophonic floor and the natural fallback for a
  monophonic-plus-simple-chords scope (§20 P0.9 option (c)). Two segmentation choices
  were required to reach F1 = 1.0 and are documented in yin_cli.cpp (offset extends one
  hop; one-hop onset debounce). The librosa.pyin floor matches at F1 = 1.0000, onset
  median 0.0067 s.

**Blocked candidates and the honest lift conditions:**
- **Magenta Onsets-and-Frames TFLite:** no published TFLite artifact exists (GitHub
  releases ship no binary assets; the magentadata GCS bucket 404s on every plausible
  URL; no Kaggle model). Separately, `tflite-runtime` ships no Python 3.12 wheels
  (latest 2.14.0, zero cp312 builds), so the interpreter cannot be installed in the
  current venv even with a model in hand. `OafTfliteWrapper` remains a documented
  skeleton (commit e2ad357). *Lift condition:* a published TFLite artifact, or an
  export path from the TF checkpoint/Hub SavedModel, plus a Python < 3.12 environment
  (or a cp312 tflite-runtime wheel).
- **Spotify Basic Pitch:** basic-pitch 0.4.0 pins `tensorflow>=2.4.1,<2.15.1`; the
  earliest Python 3.12 TensorFlow build is 2.16, so pip has no satisfiable resolution
  in the Python 3.12 venv. `BasicPitchWrapper` raises a descriptive RuntimeError.
  *Lift condition:* run in a Python < 3.12 environment or bump the basic-pitch pin.

**Harness caveat on the published comparison:** the P0.3.1 acceptance step (reproducing
a published MAESTRO number within a couple of points) is additionally blocked on data —
MAESTRO v3.0.0/v2.0.0 has no individually downloadable wavs, only 65–96 GB archives.
`validate_maestro.py` re-runs when data is obtainable. The onset-error convention for
the 0.052 s Basic Pitch comparison is marked "to confirm" in pipeline/README.md.

**Decision deferred with conditions (for the record):** the P0.3.6 ADR will be written
when (1) the P0.3.2 test set is assembled (≥ 60 min aligned audio, ≥ 24 condition
combinations — itself blocked on P0.7 hardware), and (2) the P0.3.4 on-device benchmark
has produced a device × model × delegate matrix. Until then, the engine YIN baseline is
the only scoring floor and is the default monophonic fallback per §5.3.

**Complete and green:**
- **P0.6.1 Skeleton:** Webman 2.1 on PHP 8.3, MySQL 8.0.43 + Dragonfly v1.29.0 (GHCR,
  pinned), 6 routes incl. healthz/readyz, request-id middleware, dev-auth placeholder

  guard greps in CI. RedisCommandRecorder wired into the app path.
- **P0.6.5 Load baseline (k6):** cached reads 31–35k req/s — **MET** (~6× the §13.6
  threshold of ≥ 5 000 req/s); authenticated writes 370 req/s — **NOT MET** (§13.6
  threshold ≥ 800 req/s). Root cause recorded: MySQL commit-fsync bottleneck on
  /dev/md0; async-fsync toggle measured at 8.8k req/s. The p99 < 120 ms §13.6 target is
  not yet adjudicated under the write fix.
- **P0.6.6 Drills:** reload + Dragonfly failover — 0 errors across 2M/1.8M requests,
  degraded-200 with auto-recovery ~5 s.
- **P0.6.7 ADR-0002:** coroutines OFF for HTTP workers, ON for consumer-process
  outbound fan-out; WaitGroup+Channel deadlock documented, `Workerman\Coroutine\Parallel`
  adopted (docs/adr/0002-coroutine-posture.md, re-runnable bench endpoint).

**Completed 2026-08-22 (results in docs/runbooks/soak-results-2026-08-22.md):**
- **P0.6.3 soak — MET on all load metrics, one sub-expectation NOT MET.** The
  documented 100k/1h command exhausts in 15.3 s (~6525 rps) because the driver's
  `--duration` is a deadline, not a rate limiter (Finding C; pacing fix in progress);
  the sustained-hour run therefore used a 30 M cap so the 3600 s deadline governed:
  23 436 688 requests @ 6510 rps, 0 errors, 0 bleed mismatches, worker restart count 0,
  p99 3.149 ms (minute 1) → 2.971 ms (minute 60), −5.6% (within the 10% band), RSS
  growth 0 kB (31 independent 5-minute samples, all 40408 kB; the driver's own per-minute
  RSS sampling is single-sample due to Finding B, being fixed). The MySQL-reconnect
  sub-expectation (plan §13.4.2) is **NOT MET**: a forced server-side connection kill
  returns HTTP 500 "MySQL server has gone away" on the first and second requests, with
  recovery only after the pool's ~50 s heartbeat. Root cause:
  `Webman\Database\DatabaseManager::connection()` returns the Context-cached dead
  connection during Illuminate's lost-connection retry, so the retry re-runs on the dead
  PDO. A fix + regression test is **in progress** (no commit landed as of this revision).
  The idle-reconnect check is PARTIAL: a 25-minute idle + burst returned 200 with the
  worker PID unchanged, but MySQL `wait_timeout` is 8 h, so the idle alone did not
  exercise the reconnect path.
- **P0.6.4 restart-mid-consume drill — PASS for the achievable subset.** Dragonfly
  restart mid-consume: no job loss (queue drained to 0; post-restart job consumed
  exactly once), delayed-zset promotion and the full retry path
  (consume → fail → delayed-zset → promote → consume) verified. Finding E: Dragonfly +
  phpredis returns `[]` on BRPOP timeout during a restart (no `connection lost` line),
  so a naive consumer cannot detect the restart — P1 consumer fix (treat `[]` as
  timeout, ping for connection loss). `job_outbox` table does not exist yet and no
  queue-consumer process is wired in config/process.php (both P1 items; the drill used
  the script consumer).

## 6. Content / rights status (P0.8)

**Not started.** No P0.8.2 candidate-song vetting has been performed; no provenance
records exist; no legal review has been commissioned. This is a content/legal track and
does not depend on hardware, so it can begin immediately.

**Checklist that must precede legal sign-off (P0.8.1 workflow, plan §8.5.1):** per song
against the §8.5 royalty-free-only policy:

1. **Identify the work** — composer, title, catalogue number, composition year, first
   publication year.
2. **Composer death year** — PD in life+70 territories if death year + 70 < current
   year; record the *source* of the death year, not just the number.
3. **First publication year** — covers US pre-1929-style rules and posthumous
   publication edge cases.
4. **Territory matrix** — evaluate against launch markets plus obvious next ones;
   anything not clear in all is flagged and either excluded or geo-gated
   (territory_flags_json, cleared_globally in the §8.5.6 rights record).
5. **Edition check** (§8.5.3 — the trap): a PD composition in a modern edition is not
   PD. Source only IMSLP editions explicitly marked public domain or Mutopia; record the
   specific edition. Never import modern published arrangements or scraped MusicXML of
   unknowable provenance.
6. **Record everything** in the rights record with links to sources.
7. **Second-person review** for any flagged item; counsel review for any novel category.

**P0.8.2 expectation:** 15 candidate songs vetted end-to-end by hand (incl. sourcing a
clean PD score from IMSLP/Mutopia), with at least 10 cleared globally, and a realistic
per-song time that feeds the content-throughput plan (§8.5.1: < 20 min per
straightforward PD song). **P0.8.3:** educator engaged with a first Course-1 skill
sequence draft. **P0.8.4:** one legal review of the §8.5 policy and the
arrangement/recording position.

## 7. Decision framework

Per plan §20 P0.9, the gate asks three questions: does detection work, does latency
work, and are the backend/content risks retired? Current answers:

| Question | Status | Why |
|---|---|---|
| Detection gate (chord F1 quiet/noisy, onset p95, RTF) | **UNRESOLVED — blocked, not failed** | No model artifact, no test set, no device bench. Engine YIN floor is the only scorer. |
| Latency gate (note-to-screen < 80 ms mid-tier) | **UNRESOLVED — pending** | Pipeline code-complete; zero device measurements. |
| Backend gate (soak + command surface) | **CLOSE — one defect remains** | Soak and drill complete; all load metrics pass (23.4 M requests, 0 errors, 0 bleed, RSS +0 kB). MySQL reconnect on a killed connection returns 500 until the ~50 s heartbeat — fix in progress. |
| Content/rights gate | **NOT STARTED** | Requires people (vetting, legal), not hardware. |

**The plan's fallback options if detection fails (§20 P0.9):** (a) fine-tune on our
corpus — adds 4–6 weeks and justifies a specialist hire (§21.3); (b) ship MIDI-first and
market to keyboard owners, with mic as beta; (c) narrow the promise to
monophonic-plus-simple-chords for beginner courses and defer full polyphony.
Option (d) — proceed anyway and hope — is explicitly not on the list.

**Recommendation — go-with-cuts, with the detection/latency gate deferred:**

- **The cut:** the Phase-0 gate does **not** currently certify detection or latency.
  That verdict is deferred until device evidence exists, and it must be re-run (a
  re-issued FINAL of this document) before Phase-1 completion. No Phase-1 vertical-slice
  milestone that depends on detection quality will be considered gated-passed.
- **Why go, not stop:** the hardware-free work that remains is prerequisite regardless of
  which detection path wins. SongPack v1 (P1.1) and pipeline CLI v0 (P1.2) are needed by
  every content path; the scoring engine (P1.5) is needed by every input path; the MIDI
  transport (P1.x) is needed by both option (b) and the DGX ground-truth rig. A
  stop-and-rethink would idle the entire team for the weeks it takes to source phones.
- **Why go-with-cuts, not go:** three of the plan's own Phase-1 entry criteria — "Phase 0
  gate passed or consciously re-scoped", "model ADR written", "renderer ADR written"
  (§20 Phase 1) — are not satisfiable today. The detection verdict is consciously
  re-scoped to a deferred re-run; the model ADR (P0.3.6) and renderer ADR (P0.5.4 →
  ADR-0003) are both pending device data. Starting Phase-1 implementation that depends on
  those ADRs would be pretending the gate passed.
- **Latency failures on specific devices only:** per §20 P0.9, ship a device allowlist
  with a documented "reduced accuracy" mode, and push the OEM/chipset pattern to remote
  config. The granted-property logging added in P0.2-B is the seed of that allowlist
  (devices that silently downgrade to shared mode get flagged).
- **Detection fallback posture (which option, why):** do not pre-commit. The current
  evidence — engine YIN at F1 = 1.0 on clean synthetic — supports option (c) as the
  safe default, and the MIDI hardware (DGX-520) is already the ground-truth rig for
  P0.7, so option (b) is nearly free once P0.4 lands. Option (a) (fine-tune, specialist)
  should only be invoked after the bake-off actually produces a score gap on the P0.3.2
  test set. The P0.3.6 ADR will record the choice with the bench matrix.

**Explicitly not built in Phase 0 (unchanged, §20 P0.9):** accounts, payments, real UI,
curriculum content beyond one lesson's worth of test material, the CMS, offline support.
